# พัสดุไทย.com

เว็บติดตามพัสดุรวมหลายขนส่งในที่เดียว พิมพ์เลขพัสดุครั้งเดียวแล้วระบบไล่ถามให้ทุกเจ้า

สร้างด้วย [Next.js](https://nextjs.org) (App Router)

## เริ่มพัฒนา

```bash
cp .env.example .env.local   # แล้วใส่ค่าจริงในไฟล์
npm install
npm run dev
```

เปิด http://localhost:3000

## ตรวจก่อน commit

```bash
npm run lint
npx tsc --noEmit
npm run build
```

## ตัวแปรสภาพแวดล้อม

ดูรายการทั้งหมดพร้อมคำอธิบายใน `.env.example`

ตัวแปรที่ขึ้นต้นด้วย `NEXT_PUBLIC_` **ถูกฝังลงไฟล์ JS ตอน `npm run build`** ไม่ได้อ่านตอน
runtime ถ้าเพิ่มหรือแก้ค่าเหล่านี้ต้อง build ใหม่เสมอ การ restart เฉยๆ ไม่มีผล

## ฐานข้อมูล (Supabase)

ไฟล์ SQL อยู่ใน `supabase/migrations/` รันครั้งเดียวตอนติดตั้ง ผ่าน SQL Editor
ของ Supabase dashboard หรือ `supabase db push` ถ้าใช้ CLI

`0001_saved_trackings.sql` สร้างตารางประวัติที่ผู้ใช้กดบันทึก พร้อมเปิด RLS และ
policy ครบทั้ง SELECT / INSERT / UPDATE / DELETE โดยผูกกับ `auth.uid() = user_id`

**ห้ามข้ามการเปิด RLS** เพราะเบราว์เซอร์ใช้ anon key ยิงเข้า PostgREST ได้โดยตรง
ถ้าไม่เปิด ผู้ใช้ที่ล็อกอินอยู่คนไหนก็อ่านและลบประวัติของคนอื่นได้ทั้งหมด

⚠️ **`0008` ต้องรันก่อน deploy โค้ดเสมอ ห้ามสลับลำดับ** ต่างจากไฟล์อื่นตรงที่มัน

`SAVED_TRACKING_COLUMNS`) ถ้า deploy ก่อน หน้าประวัติกับปุ่มบันทึกจะพังทันที
เพราะ PostgREST ปฏิเสธ query ที่อ้างคอลัมน์ที่ไม่มี

⚠️ `0007` มีฟังก์ชัน **security definer ตัวเดียวในโปรเจกต์** (`admin_member_stats`)
เพราะต้องนับแถวใน `auth.users` ซึ่งอยู่นอก schema `public` มันคืนได้แค่ `count(*)`
ล็อก `search_path` และ grant ให้ `service_role` เจ้าเดียว — มีเทสต์เฝ้าไว้ที่
`lib/admin-privacy.test.ts`

## ตรวจค่า environment variable

```bash
npm run check-env                        # เทียบค่าในไฟล์กับค่าที่โปรแกรมอ่านได้จริง
npm run check-env -- --call-thailand-post # ยิงขอ token จริงเทียบสองค่า
```

มีสองกรณีที่ทำให้ "curl ใช้ได้แต่แอปได้ 401" โดยที่แอปไม่ error ตอนอ่าน env
(ตัวแปรมีค่าอยู่ แค่เป็นค่าที่ผิด) และมองไม่เห็นจากการดูไฟล์เฉยๆ:

1. **ค่ามีเครื่องหมาย `$`** — Next ใช้ dotenv-expand ตีความว่าเป็นชื่อตัวแปรอื่น
   แล้วตัดตั้งแต่ `$` เป็นต้นไปทิ้ง (วัดจริง: ค่ายาว 17 ตัวอักษรเหลือ 3)
   แก้ด้วยการเขียนเป็น `\$` ในไฟล์

2. **มีค่าเดิมค้างอยู่ใน `process.env` แล้ว** — เช่น PM2 จำ env ตอนสร้าง process
   ไว้, มีใน `ecosystem.config.js` หรือ `export` ค้างใน shell **Next จะไม่เขียนทับ
   ค่าที่มีอยู่แล้ว** ไฟล์ `.env.local` จึงถูกมองข้ามทั้งไฟล์ และ `pm2 restart`
   ก็ไม่ช่วย เพราะค่ายังถูกส่งเข้ามาจากข้างนอกเหมือนเดิม

`npm run check-env` ตรวจทั้งสองกรณีนี้ให้ โดยแสดงแค่ความยาวกับ checksum ไม่พิมพ์
ค่าจริงของ key ออกมา

## เพดานการยิง Track123 และการอ่าน log

Track123 จำกัด **5 request/วินาที ต่อ endpoint** เกินแล้วตอบ code `A0706` กลับมา
ผู้ใช้แค่ 3–4 คนก็ชนได้ เพราะการค้นหา 1 ครั้งอาจยิงหลายครั้ง (ระบุขนส่ง + ตรวจจับเอง +
ลองซ้ำ) สี่ชั้นที่กันไว้:

| ชั้น | ไฟล์ | ทำอะไร |
| --- | --- | --- |
| เดาขนส่งจาก prefix | `lib/carriers/courier-prefix.ts` | เลขขึ้นต้น `SPXTH` ข้ามไปรษณีย์ไทย ยิงตรงไป `shopee-xpress-th` ประหยัด 1 call และเร็วขึ้น 1 รอบ |
| รวมคำขอซ้ำ | `lib/inflight.ts` | เลขเดียวกันที่กำลังรอผลอยู่แชร์ promise เดียวกัน ไม่ยิงซ้ำ |
| คิวจำกัดอัตรา | `lib/rate-limit-queue.ts` | ยิงได้ไม่เกิน 3 ครั้ง/วินาที ที่เกินเข้าแถวรอ ไม่ถูกทิ้ง |
| ลองใหม่อัตโนมัติ | `lib/carriers/track123-gateway.ts` | เจอ `A0706` แล้วหน่วง 500ms → 1s → 2s ก่อนยอมแพ้ |

ผู้ใช้จะเห็นข้อความ "คิวค้นหาหนาแน่น" ก็ต่อเมื่อทั้งสี่ชั้นเอาไม่อยู่ ระหว่างที่ยัง
รอคิวอยู่หน้าเว็บยังแสดงสถานะกำลังค้นหาตามปกติ

เลขที่ prefix ฟันธงว่าเป็นขนส่งเจ้าอื่น **ข้ามไปรษณีย์ไทยไปเลย** เพราะเลขทรงนั้น
ไม่มีทางอยู่ในระบบไปรษณีย์ไทย ส่วนเลขที่ prefix ไม่ฟันธงยังถามไปรษณีย์ไทยก่อนตามเดิม
(ฟรีและไม่จำกัดจำนวนครั้ง)

การเพิ่ม prefix เจ้าใหม่ทำได้ด้วยการเติมแถวใน `COURIER_PREFIXES` แถวเดียว —
เกณฑ์ที่ต้องผ่านก่อนเติมอยู่ในหัวไฟล์นั้น และต้องเข้มเป็นพิเศษ เพราะแถวที่ผิดแปลว่า
เลขกลุ่มนั้นจะไม่ถูกถามไปรษณีย์ไทยอีกเลย

### นับจำนวนการยิงจริงจาก pm2

ทุก request ที่ออกไปหา Track123 จริงถูกเขียนเป็น log บรรทัดเดียว:

```
[track123] ts=1756531234567 no=SPXTH046012345678 courier=shopee-xpress-th attempt=1/4 queued=3 wait=334ms took=287ms result=rate_limited upstream=A0706
```

- `queued` — มีคำขออัดอยู่ในคิวกี่ตัว ณ ตอนที่ตัวนี้เข้าคิว (`1` = คิวว่าง)
- `wait` — รอคิวกี่ ms ก่อนได้ยิง
- `attempt=n/4` — ยิงเป็นครั้งที่เท่าไรของคำขอนั้น (รวมรอบที่ลองใหม่)
- `result` — `ok` หรือสาเหตุที่พลาด, `upstream` คือ code ดิบของ Track123

```bash
pm2 logs --nostream --lines 5000 | grep -c '\[track123\]'        # ยิงไปทั้งหมดกี่ครั้ง
pm2 logs --nostream --lines 5000 | grep 'result=rate_limited'    # ชนลิมิตตอนไหนบ้าง
pm2 logs --nostream --lines 5000 | grep '\[track123\]' | grep -v 'queued=1 '   # จังหวะที่คิวอัดกัน
```

## Cache ผลติดตามพัสดุ (สองชั้น)

```
คำค้นเข้ามา → ชั้น 1 memory → ชั้น 2 Supabase → ยิง API จริง
                  ↑ เร็วสุด        ↑ รอด restart      ↓
                  └────────── เขียนกลับทั้งสองชั้น ────┘
```

| ชั้น | ไฟล์ | รอด restart | ใช้ร่วมทุก instance |
| --- | --- | --- | --- |
| 1. memory | `lib/cache.ts` | ✗ | ✗ |
| 2. Supabase | `lib/supabase/tracking-cache.ts` | ✓ | ✓ |

ตัวประกอบสองชั้นอยู่ที่ `lib/tracking-cache.ts`

โควตาของ Track123 นับเป็น **จำนวนเลขพัสดุต่อรอบบิล ไม่ใช่จำนวน request** การยิงเลขเดิม
ซ้ำจึงไม่เสียโควตาเพิ่ม เป้าหมายของ cache คือลดจำนวน request (เพดาน 5 req/s) ลดเวลารอ
ของผู้ใช้ และมีของสำรองไว้แสดงในวันที่ระบบขนส่งล่ม

### TTL ตามสถานะ

| สถานะ | TTL | เหตุผล |
| --- | --- | --- |
| `delivered` | 30 วัน | ถึงมือผู้รับแล้ว ไม่มีทางเปลี่ยนอีก |
| `exception` | 3 ชั่วโมง | ไม่ใช่สถานะจบจริง — "นำจ่ายไม่สำเร็จ" มักถูกส่งใหม่วันถัดไป |
| `pending` / `in_transit` | 2 ชั่วโมง | ขยับเป็นช่วงๆ |
| `out_for_delivery` | 15 นาที | เปลี่ยนได้ทุกนาที และเป็นช่วงที่ผู้ใช้เช็คถี่สุด |

แก้ที่ `TTL_MS` ใน `lib/cache.ts` ที่เดียว

### วันที่ระบบขนส่งล่ม

ถ้ายิง API ไม่สำเร็จเพราะ **ระบบมีปัญหา** (ขนส่งล่ม, โควตาหมด, ชนลิมิตจนเอาไม่อยู่)
แต่มีข้อมูลเก่าค้างใน cache ระบบจะแสดงข้อมูลเก่านั้นพร้อมป้าย "ระบบขนส่งไม่ตอบตอนนี้"
และเวลาที่ดึงข้อมูลมา — ผู้ใช้ได้คำตอบ ไม่ใช่หน้าจอ error

`not_found` กับ `invalid_tracking_number` **ไม่** เข้าเงื่อนไขนี้ เพราะเป็นคำตอบจริงที่
ผู้ใช้ต้องได้เห็น ถ้าเอาข้อมูลเก่ามาบัง พัสดุที่หลุดออกจากระบบขนส่งไปแล้วจะดูเหมือน
ยังตามได้อยู่ตลอดกาล

### ความปลอดภัยของตาราง

ตาราง `public.tracking_cache` เป็น **ของกลาง ไม่มีคอลัมน์ `user_id` และห้ามเพิ่ม** —
ถ้าเก็บว่าใครค้นเลขอะไร ตารางจะกลายเป็นบันทึกพฤติกรรมผู้ใช้ทันที

เข้าถึงได้จากฝั่งเซิร์ฟเวอร์ด้วย service role key เท่านั้น กันไว้สามชั้น:

1. `revoke all` จาก `anon` และ `authenticated` ในไฟล์ migration
2. เปิด RLS ไว้โดย **ไม่มี policy เลย** — Postgres ปฏิเสธทุกแถวเป็นค่าเริ่มต้น
3. เทสต์ใน `lib/supabase/tracking-cache.test.ts` อ่านซอร์สจริงแล้วยืนยันว่าไม่มี
   client component ไหน import ไฟล์ที่ถือ key และมีไฟล์เดียวที่แตะชื่อตาราง

## นับ cache hit rate จาก pm2

log สองชนิดที่คู่กัน:

| log | หนึ่งบรรทัดต่อ |
| --- | --- |
| `[track]` | หนึ่งการค้นหาของผู้ใช้ ไม่ว่าจะได้คำตอบจากชั้นไหน |
| `[track123]` | หนึ่ง request ที่ออกไปหา Track123 จริง |

```
[track] ts=1756531234567 no=EY145587896TH route=track source=memory stale=no shared=no took=3ms
[track] ts=1756531240120 no=SPXTH046012345678 route=track source=supabase stale=yes shared=no took=1503ms reason=rate_limited
```

- `source` — `memory` / `supabase` / `api` / `error`
- `stale=yes` — แสดงข้อมูลเก่าเพราะยิงของสดไม่สำเร็จ
- `route` — `track` (หน้าค้นหา) หรือ `saved` (กดบันทึกประวัติ)

```bash
L='pm2 logs --nostream --lines 20000'

$L | grep -c '\[track\] '                    # ค้นหาทั้งหมดกี่ครั้ง
$L | grep -c 'source=memory'                 # จบที่ชั้น memory
$L | grep -c 'source=supabase'               # จบที่ชั้น Supabase
$L | grep -c 'source=api'                    # ต้องยิง API จริง
$L | grep -c 'stale=yes'                     # ต้องใช้ข้อมูลสำรอง (ขนส่งมีปัญหา)
```

hit rate = `(memory + supabase) / ทั้งหมด` — ถ้าตัวเลข `source=api` ยังสูงหลังใช้งาน
ไปสักพัก แปลว่า TTL สั้นเกินไปสำหรับสถานะที่ถูกค้นบ่อย

## แผนที่และพิกัดสาขา

ปัญหาเดิม: ข้อความสถานที่จากขนส่งจำนวนมากเป็น **รหัสสาขาภายใน** ไม่ใช่ที่อยู่ เช่น
`ACRAI-B - เมืองเชียงราย` เราเคยส่งทั้งก้อนให้ Google Geocoding ซึ่งไม่รู้จักรหัสพวกนี้
Google จึงเดาจากคำที่พอเดาได้ (`เชียงราย`) แล้วคืนหมุดกลางเมือง ผู้ใช้เห็นแล้วเข้าใจว่า
พัสดุอยู่ตรงนั้นจริง

หลักการใหม่: **ถ้าไม่รู้ว่าอยู่ไหนจริงๆ ห้ามปักหมุด**

### ลำดับการหาพิกัด

`lib/location-resolve.ts` — ตัดสินจาก `lib/branch-location.ts` ว่าข้อความเป็นแบบไหน

| ข้อความ | ทำอะไร |
| --- | --- |
| รหัสสาขา (`ACRAI-B`, `NO4_HUB`, `SOCN`) | หาจาก `carrier_branches` เท่านั้น เจอ → ปักหมุด · ไม่เจอ → **แสดงชื่อเป็นข้อความ** + จดลง `unknown_branches` แล้ว[ลองไปขอที่อยู่มาเติมเอง](#เติมพิกัดสาขาอัตโนมัติ) |
| ที่อยู่จริง (`ศูนย์ไปรษณีย์หลักสี่`, `Bangkok`) | ดู `geocode_cache` ก่อน ไม่มีค่อยถาม Google แล้วเก็บผลถาวร (เก็บผลที่หาไม่เจอด้วย) · ผลต้องผ่าน[เกณฑ์ความละเอียด](#เกณฑ์ความละเอียดของพิกัด) เหมือนกัน |
| อ่านไม่ออก | ไม่ปักหมุด ไม่เสีย quota ไปกับการเดา |

ตัวแยกรหัสสาขารับสองรูป: ตัวพิมพ์ใหญ่ที่มีขีด/ขีดล่างคั่นหรือมีตัวเลขปน (`ACRAI-B`)
**และ** ข้อความที่เป็นตัวพิมพ์ใหญ่ล้วนทั้งก้อนยาว 2–10 ตัวอักษร (`SOCN`, และ `BANGKOK`
ที่มาโดดๆ ด้วย — เหตุผลของการแลกนี้อยู่ใน[หัวข้อเติมพิกัดสาขาอัตโนมัติ](#ทุกกรณีที่จบด้วย-ไม่มีแผนที่-ถูกจดไว้หมด))

⚠️ ห้ามเอา **ชื่อ** สาขาที่ไม่รู้พิกัดไป geocode ต่อ — จะได้หมุดกลางอำเภอ ซึ่งคือปัญหาเดิมเป๊ะๆ
มีเทสต์เฝ้าไว้ว่าไม่มี input ไหนที่เป็นรหัสสาขาแล้วหลุดไปถึง Google ได้

### แผนที่เป็นภาพนิ่ง

หน้าประวัติเปลี่ยนจาก Maps Embed (iframe โต้ตอบได้) เป็นภาพนิ่งจาก Maps Static API
ที่ยิงผ่าน `/api/map` ของเราเอง

- คีย์ไม่เคยออกจากเครื่อง (Embed บังคับให้ใส่คีย์ลงใน URL ที่ผู้ใช้เปิดดู source เห็น)
- ขนาดกับระดับซูมกำหนดตายตัวฝั่งเซิร์ฟเวอร์ ไม่ให้ client เลือกเอง — กันคนยิงขอภาพ
  ใหญ่ๆ รัวๆ ให้โควตาหมด และทำให้ทุกคนที่ดูพิกัดเดียวกันได้ URL เดียวกันเป๊ะ
- `Cache-Control: public, max-age=2592000` (30 วัน) — แผนที่ฐานของพิกัดเดิมไม่เปลี่ยน
- ใช้ `GOOGLE_MAPS_API_KEY` ตัวเดิมที่จำกัดด้วย IP · `GOOGLE_MAPS_EMBED_KEY` **เลิกใช้แล้ว**

## สองผู้ให้บริการ สลับใช้ตามความถนัด

ทั้ง Track123 และ ETrackings เสียเงินรายเดือนทั้งคู่ ระบบจึงใช้ **ทั้งสองเจ้าจริง
ทุกวัน** ไม่ใช่มีเจ้าหนึ่งเป็นตัวสำรองที่แทบไม่ถูกแตะ — ของที่จ่ายแล้วไม่ได้ใช้คือ
ของที่เสียเปล่า และเจ้าที่ไม่เคยถูกแตะจะไปพังตอนที่เราต้องใช้จริงโดยไม่มีใครรู้มาก่อน

### ลำดับที่เลือกใช้

| สถานการณ์ | ลำดับ |
| --- | --- |
| ไม่รู้ว่าเป็นขนส่งเจ้าไหน | ไปรษณีย์ไทย → Track123 |
| `prefix` ฟันธงได้ + ETrackings รองรับ (เช่น `SPXTH`) | **ETrackings → Track123** (ข้ามไปรษณีย์ไทย) |
| เคยค้นเลขนี้สำเร็จแล้ว + ETrackings รองรับ courier นั้น | ไปรษณีย์ไทย → **ETrackings → Track123** |
| รู้ courier แต่ ETrackings ไม่รองรับ | Track123 เจ้าเดียว |

### "รู้ว่าเป็นเจ้าไหน" มาได้สองทาง

1. **`prefix` ฟันธง** — เชื่อถือได้ที่สุด แต่ครอบคลุมน้อย
2. **`tracking_cache` จำ courier ของครั้งก่อนไว้** — ตารางนั้นมีคอลัมน์
   `courier_code` อยู่แล้ว และ `lookupTracking()` คืนแถวที่หมดอายุแล้วด้วย
   (ธง `stale`) มันจึงเป็นความจำ "เลขนี้คือขนส่งเจ้าไหน" ที่มีอยู่แล้วโดยไม่ต้อง
   เก็บอะไรเพิ่มเลย

ทางที่สองสำคัญมากในทางปฏิบัติ เพราะ **เลข SPX ในไทยส่วนใหญ่ขึ้นต้นด้วย `TH`
ไม่ใช่ `SPXTH`** (`SPXTH…` เจอเฉพาะพัสดุข้ามประเทศ) และรูป `TH` + ตัวเลข +
ตัวอักษร **ใช้ร่วมกับ Flash Express** (ยืนยันด้วยเลขจริงแล้ว: `TH5401714MR03P`
เป็นของ Flash) จึงฟันธงจาก prefix ไม่ได้ตลอดกาล

⚠️ **ห้ามเติม `TH` ลงตาราง `COURIER_PREFIXES`** — ตกเกณฑ์ข้อ 1 ("เป็นของเจ้านั้น
เจ้าเดียว") การเติมเข้าไปคือการบังคับยิงผิดเจ้าตั้งแต่ครั้งแรก ซึ่งแย่กว่าปล่อยให้
auto-detect ทำงาน ยึด mapping รายเลขที่ยืนยันแล้วอย่างเดียว

ผลคือ **การค้นครั้งแรกใช้ Track123 ส่วนครั้งต่อไปของเลขเดิมใช้ ETrackings ได้**
ซึ่งตรงกับพฤติกรรมจริงของเว็บติดตามพัสดุ (คนเช็คซ้ำทุกวัน) และเป็นสิ่งที่ปลดล็อก
การเติมพิกัดสาขาให้ทำงานกับเลขส่วนใหญ่

ความถนัดของแต่ละเจ้า:

- **ETrackings** — บังคับให้ระบุขนส่งเอง (เลขที่เดาไม่ออกใช้ไม่ได้เลย) แต่คืน
  ข้อความไทยล้วน **และที่อยู่เต็มของสาขา** ซึ่งเป็นวัตถุดิบเดียวที่ทำให้เติมพิกัด
  สาขาอัตโนมัติได้
- **Track123** — ตรวจจับขนส่งเองได้ จึงเป็นเจ้าเดียวที่รับมือเลขที่เดาไม่ออก

ไปรษณีย์ไทยไม่เปลี่ยน: ต่อตรง ฟรี ไม่จำกัดครั้ง และยังถูกถามก่อนเสมอเมื่อ prefix
ไม่ฟันธง

### กติกาการไปต่อเจ้าถัดไป

| เจ้าแรกตอบอะไร | ไปต่อไหม |
| --- | --- |
| พังด้วยเหตุระบบ (ล่ม / โควตาหมด / breaker ตัด) | **ไปต่อเสมอ** ทั้งสองทิศทาง |
| ETrackings ตอบ "ไม่พบ" | ไปต่อ — มันยิงครั้งเดียวด้วยขนส่งที่เราเดาให้ เดาผิดก็ตอบไม่พบทั้งที่พัสดุมีจริง |
| Track123 ตอบ "ไม่พบ" | **หยุด** — มันตรวจจับเองแล้วยังไล่ระบุเจาะจงซ้ำอีกหลายเจ้า คำว่าไม่พบหนักแน่นพอ |

error ที่ส่งขึ้นไปเมื่อพังทั้งคู่คือ **ของ Track123 เสมอ** เพราะชั้นบนใช้ code นั้น
ตัดสินว่าจะคืนข้อมูลเก่าจาก cache หรือไม่

### Circuit breaker

`lib/circuit-breaker.ts` ใช้กับทั้งสองเจ้า เจ้าไหนวงจรถูกตัดก็สลับไปอีกเจ้าอัตโนมัติ

| | Track123 | ETrackings |
| --- | --- | --- |
| พังกี่ครั้งถึงตัดวงจร | 5 ครั้งใน 1 นาที | **3 ครั้งใน 1 นาที** |
| พักนานเท่าไร | 30 วินาที | **60 วินาที** |

ETrackings ไวกว่าและพักนานกว่าโดยตั้งใจ เพราะทุกครั้งที่ยิงแล้วพังคือโควตาที่จ่ายไป
โดยไม่ได้อะไรกลับมา

ระหว่างวงจรถูกตัด คำขอถูกปฏิเสธทันทีโดยไม่ยิงและไม่เข้าคิว (และ**ไม่นับโควตา**)
ผู้ใช้จึงไม่ต้องรอ timeout ทีละคน ครบเวลาพักแล้วจะปล่อยผ่าน **คำขอเดียว** เพื่อ
ลองแตะดู สำเร็จ → กลับมาปกติ · พังอีก → พักใหม่ตั้งแต่ต้น

นับเฉพาะความล้มเหลวที่แปลว่าปลายทางมีปัญหา (`rate_limited` / `network_error` /
`upstream_error` / `auth_failed`) **ไม่นับ `not_found`** เพราะนั่นคือคำตอบที่ถูกต้อง
ของปลายทางที่ทำงานปกติ — ถ้านับด้วย วันที่คนค้นเลขผิดกันเยอะๆ วงจรจะถูกตัดทั้งที่
ปลายทางไม่ได้เป็นอะไรเลย

### โควตาและการเอียงหนีเพดาน

`lib/provider-usage.ts` นับ **จำนวน request ที่ยิงออกไปจริง** ของแต่ละเจ้า เก็บลง
ตาราง `provider_usage` (แยกตามเดือนแบบเวลาไทย) ตัวนับจึงรอด restart และรวมยอดข้าม
instance ได้ ทุกครั้งที่นับ ฐานข้อมูลคืนยอดจริงกลับมาให้ตัวนับใน memory ปรับตาม

เมื่อเจ้าที่ควรได้ไปก่อน **ใช้ไปถึงสัดส่วนที่ตั้งไว้** (`PROVIDER_QUOTA_LEAN_RATIO`
ค่าเริ่มต้น 0.8) และอีกเจ้ายังไม่ใกล้ → สลับลำดับ "ใกล้ชนเพดาน" ไม่ใช่ "ห้ามใช้"
เจ้านั้นยังอยู่ในลำดับที่สองเสมอ เพราะการปฏิเสธคำค้นทั้งที่ยังมีโควตาเหลือแย่กว่า
การใช้โควตาที่เหลืออยู่ · ทั้งคู่ใกล้ชนเพดานพร้อมกัน → ไม่สลับ

| env | ค่าเริ่มต้น |
| --- | --- |
| `TRACK123_MONTHLY_CALL_LIMIT` | 1000 |
| `ETRACKINGS_MONTHLY_CALL_LIMIT` | 50 (เพดานแผนฟรี) |
| `PROVIDER_QUOTA_LEAN_RATIO` | 0.8 |

⚠️ **Track123 คิดเงินเป็นรายเลขพัสดุต่อรอบบิล ไม่ใช่รายคำขอ** ยอดที่เรานับจึงสูงกว่า
ยอดบิลเสมอ ใช้เป็นสัญญาณเตือนว่า "เริ่มใช้เยอะแล้ว" ไม่ใช่ยอดที่เอาไปกระทบยอดได้
ควรตั้งเพดานให้ตรงกับแผนที่จ่ายจริง

## เติมพิกัดสาขาอัตโนมัติ

ETrackings ห้อย **ที่อยู่เต็มของสาขา** มาท้าย description ให้ด้วย:

```
09:28 พัสดุถึงสาขาปลายทาง: ACRAI-B - เมืองเชียงราย - อยู่ที่ TH จังหวัดเชียงราย
57000 อำเภอเมืองเชียงราย 639 หมู่ที่1 ตำบลบ้านดู่ อำเภอเมืองเชียงราย
จังหวัดเชียงราย 57100
```

รหัส `ACRAI-B` ไม่มีทาง geocode ได้ แต่ที่อยู่นั้นได้ `lib/branch-harvest.ts` จึงแยก
ที่อยู่ออกมา หาพิกัด แล้วเขียนลง `carrier_branches` ให้เอง สาขาหนึ่งจ่ายราคาครั้งเดียว
แล้วใช้ได้ตลอด กับทุกคน และกับ**ทุกขนส่ง** ที่ส่งรหัสสาขาเดียวกันมา — `carrier_branches`
เป็นของกลาง ไม่ผูกกับผู้ให้บริการ API เจ้าใดเจ้าหนึ่ง

การแยกที่อยู่ตัดส่วนที่ซ้ำซ้อนนำหน้าทิ้ง (`TH จังหวัดเชียงราย 57000 อำเภอเมืองเชียงราย`)
เหลือเฉพาะที่อยู่ไทยมาตรฐานตั้งแต่บ้านเลขที่ถึงรหัสไปรษณีย์ ถ้าหาจุดตั้งต้นไม่เจอ
หรือไม่มีจังหวัด/รหัสไปรษณีย์ **จะไม่เดา** — จดลง `unknown_branches` แทน

### สองกติกาที่ห้ามผ่อน

1. **ห้ามเขียนพิกัดระดับ "พื้นที่" ลง `carrier_branches`** ตารางนั้นคือที่ที่ทั้งระบบ
   เชื่อว่าถูกต้องแน่นอน เกณฑ์คือ[ชั้นความละเอียดที่วัดได้](#เกณฑ์ความละเอียดของพิกัด)
   ไม่ใช่ชนิดของคำตอบที่ Google ส่งมา
2. **ห้ามทับของที่มีอยู่แล้ว** พิกัดที่แอดมินกรอกเองถูกต้องกว่าเสมอ (บังคับที่ชั้น
   ข้อมูลด้วย `insert` ไม่ใช่ `upsert`)

แถวที่ระบบเติมเองมี `updated_by = auto:etrackings` และ `note` เก็บที่อยู่ที่ใช้หาพิกัด
ไว้ให้แอดมินตรวจย้อนได้

### กลไกกันเผาโควตา — สี่ด่านซ้อนกัน

เมื่อ Track123 คืนรหัสสาขาเปล่าๆ ที่ยังไม่มีพิกัด ระบบจะยิง ETrackings **หนึ่งครั้ง**
เพื่อขอที่อยู่มาเติม ด่านทั้งสี่เรียงจากถูกไปแพง ด่านที่เขียนฐานข้อมูลอยู่หลังสุดเสมอ

| # | ด่าน | ทำอะไร |
| --- | --- | --- |
| 0 | ตั้งค่าแล้วหรือยัง | ไม่มีคีย์ → ไม่ทำอะไรเลย |
| 1 | รู้ courier ไหม (prefix **หรือ** ที่ยืนยันแล้วจากผลที่เพิ่งค้น) | ETrackings ตามเลขนี้ไม่ได้ → ยิงไปก็ทิ้งโควตาแน่นอน |
| 2 | โควตาใกล้เต็มหรือยัง | ใกล้เต็ม → เก็บไว้ให้การค้นหาจริงของผู้ใช้ก่อน การเติมพิกัดรอวันหลังได้ |
| 3 | งบต่อวันของโปรเซส | `BRANCH_PROBE_DAILY_LIMIT` (ค่าเริ่มต้น 10) กันกรณีสาขาใหม่โผล่พรวดเดียวเป็นร้อย |
| 4 | จองสิทธิ์ต่อสาขาในฐานข้อมูล | `claim_branch_probe()` — **atomic** สองคำขอพร้อมกันมีแค่หนึ่งที่ได้สิทธิ์ ต่อให้มาจากคนละ instance |

ด่าน 4 คือตัวรับประกันว่า **สาขาหนึ่งจ่ายโควตาครั้งเดียว** สาขาที่ถามแล้วไม่ได้ที่อยู่
จะถูกล็อกไว้จนพ้น `BRANCH_PROBE_COOLDOWN_HOURS` (ค่าเริ่มต้น 168 ชั่วโมง = 7 วัน)
ไม่ใช่ห้ามถามตลอดกาล เพราะขนส่งอาจเริ่มส่งที่อยู่มาในภายหลัง

### ทุกกรณีที่จบด้วย "ไม่มีแผนที่" ถูกจดไว้หมด

`unknown_branches` มีคอลัมน์ `kind` แล้ว จึงเก็บได้ครบทั้งสามแบบ ไม่ใช่เฉพาะรหัสสาขา
เหมือนเดิม:

| `kind` | ตัวอย่าง |
| --- | --- |
| `branch` | `ACRAI-B`, `NO4_HUB`, และ**รหัสล้วนอย่าง `SOCN`** |
| `address` | ข้อความที่ดูเหมือนที่อยู่แต่ Google หาไม่เจอ |
| `unknown` | ข้อความที่อ่านไม่ออกว่าเป็นอะไร |

⚠️ ตัวแยกรหัสสาขาถูกขยายให้จับ **ข้อความที่เป็นตัวพิมพ์ใหญ่ล้วนทั้งก้อน ยาว 2–10
ตัวอักษร** ด้วย (`SOCN`) เดิมข้อความแบบนี้ผ่านเกณฑ์ "ดูเหมือนที่อยู่" แล้วถูกส่งให้
Google ซึ่งเป็นรูรั่วที่เหลืออยู่ของหลักการ "เมื่อไม่แน่ใจ ห้ามปักหมุด"

กติกานี้จับคำอย่าง `BANGKOK` ที่มาโดดๆ ไปด้วย **โดยตั้งใจ** — แลกการเสียหมุดของ
คำที่หาพิกัดได้จริง (กู้คืนได้ด้วยการให้แอดมินกรอกพิกัด) กับการไม่ปักหมุดมั่วให้
รหัสสาขา (กู้ไม่ได้ เพราะผู้ใช้แยกไม่ออกว่าข้อมูลผิด) · `SHENZHEN sorting centre`
ที่มีเนื้อความอื่นต่อท้ายยังหาพิกัดได้ตามปกติ

พิกัดที่แอดมินกรอกไว้ใช้ได้กับทุก `kind` ไม่ใช่เฉพาะรหัสสาขา — ทุกเส้นทางเปิดตาราง
`carrier_branches` ดูด้วยข้อความนั้นตรงๆ อีกรอบก่อนยอมแพ้

## เกณฑ์ความละเอียดของพิกัด

**หลักการ:** ปักหมุดได้ก็ต่อเมื่อรู้ว่าแม่นแค่ไหน และถ้าไม่แม่นต้องบอกผู้ใช้ตรงๆ

### ทำไมไม่ใช้ `location_type` ของ Google

เกณฑ์รุ่นแรกรับเฉพาะ `ROOFTOP` กับ `RANGE_INTERPOLATED` ผลจากการใช้จริงคือ
**ไม่เคยผ่านเลยสักครั้ง** — ที่อยู่ไทยแบบ `639 หมู่ที่1 ตำบลบ้านดู่ …` Google คืน
`GEOMETRIC_CENTER` หรือ `APPROXIMATE` ให้เสมอ การเก็บพิกัดสาขาอัตโนมัติจึงตายสนิท

แต่จะผ่อนให้รับสองค่านั้นเฉยๆ ก็ไม่ได้ เพราะ `location_type` บอกแค่ *วิธี* ที่ Google
ได้พิกัดมา ไม่ได้บอก *ขนาด* ของสิ่งที่จับได้ — `GEOMETRIC_CENTER` เป็นได้ทั้ง
"กลางถนนซอยหนึ่ง" และ "กลางตำบล" ส่วน `APPROXIMATE` เป็นได้ทั้งตำบลและทั้งจังหวัด

### สิ่งที่ใช้แทน — วัดขนาดจริง

| สัญญาณ | ใช้ยังไง |
| --- | --- |
| `geometry.bounds` / `viewport` | ครึ่งเส้นทแยงมุมเป็นเมตร = **รัศมีความคลาดเคลื่อน** บ้านเลขที่ ~100 ม. · ตำบล ~3–8 กม. · อำเภอ 15–40 กม. |
| `types[]` | เจอ `administrative_area_level_1/2` หรือ `country` → ปฏิเสธทันที ไม่ว่ากรอบจะเล็กแค่ไหน |
| `partial_match` | Google บอกเองว่าจับได้ไม่ครบ → ปฏิเสธทันที |

### สามชั้น

| รัศมี | ชั้น | ผล |
| --- | --- | --- |
| ≤ 150 ม. | `exact` | ปักหมุดตามปกติ |
| 150 ม. – 5 กม. | `approximate` | ปักหมุด + **ป้าย "ตำแหน่งโดยประมาณ"** + ซูมออกจาก z15 เป็น z13 |
| > 5 กม. หรือติดด่าน `types`/`partial_match` | `area` | **ไม่ปักหมุด** จดลง `unknown_branches` |

เพดาน 5 กม. ปรับผ่าน `GEOCODE_MAX_ACCURACY_METERS` ได้ · **ด่าน `types` กับ
`partial_match` ไม่เปิดให้ปรับ** จุดกึ่งกลางของอำเภอไม่ใช่ที่ตั้งของอะไรทั้งนั้น
ไม่ว่าเพดานจะกว้างแค่ไหน

ฐานข้อมูลเก็บ **ค่าที่วัดได้** (`accuracy_meters`, `area_only`) ไม่ใช่คำตัดสิน ชั้นถูก
คำนวณสดทุกครั้งที่อ่าน การปรับเพดานจึงมีผลกับของที่ cache ไว้แล้วทันที ไม่ต้องล้าง cache
และไม่ต้องยิงถาม Google ใหม่

### ครอบคลุมทั้งสองเส้นทาง

เกณฑ์นี้ใช้กับ **ทั้ง**การเติมพิกัดสาขาอัตโนมัติ **และ**การ geocode ข้อความประเภท
ที่อยู่ตามปกติ — เดิมเส้นทางหลังปักหมุดทุกอย่างที่ Google คืนมาโดยไม่บอกอะไรเลย
ต่อให้เป็นหมุดกลางจังหวัดก็ตาม ซึ่งเป็นรูสุดท้ายของหลักการ "เมื่อไม่แน่ใจ ห้ามปักหมุด"

⚠️ **ผลข้างเคียงที่ต้องรู้:** หลัง deploy หมุดของข้อความกว้างๆ อย่าง `เมืองเชียงราย`
จะหายไป (กลายเป็นข้อความ + เข้าคิวใน `unknown_branches` ให้แอดมินเติมพิกัดที่ถูกต้อง)
นี่คือพฤติกรรมที่ตั้งใจ ไม่ใช่ regression

ความต่างสองอย่างระหว่างสองเส้นทาง เพราะข้อกำหนดต่างกันจริง:

- **แถวเก่าใน cache ที่ไม่มีผลการวัด** (`accuracy_meters` เป็น `null`) — เส้นทางแสดงผล
  ยังปักหมุดให้พร้อมป้าย "โดยประมาณ" ส่วนเส้นทางเขียน `carrier_branches` ปฏิเสธ
  เพราะตารางนั้นเป็นของที่ทั้งระบบเชื่อว่าถูก ของที่ไม่รู้ที่มาไม่ควรเข้าไป
- **แถวเก่าใน `saved_trackings`** (`last_location_accuracy` เป็น `null`) — **ไม่ขึ้นป้าย**
  เพราะเราไม่รู้จริงๆ ว่าหมุดนั้นแม่นแค่ไหน การเดาว่า "ไม่แม่น" แล้วติดป้ายให้ทุกแถวเก่า
  คือการบอกสิ่งที่เราไม่รู้ ไม่ต่างจากการเดาว่าแม่น · แถวจะได้ค่าเองเมื่อผู้ใช้กด
  บันทึกเลขนั้นซ้ำ

## เมื่อเจอ "permission denied" กับตารางของกลาง

เคยเกิดจริงบน production หลัง deploy #13 — cache ถาวรไม่เคยทำงานเลย
(`tracking_cache` มี 0 แถว) หน้า `/admin/branches` ว่างเปล่า และแผนที่ไม่ขึ้น

```
[track-cache] อ่าน ... ล้มเหลว: permission denied for table tracking_cache
[locations] บันทึกสาขาที่ไม่รู้จัก ล้มเหลว: permission denied for function record_unknown_branch
```

`permission denied` แปลว่า request **ออกไปถึงและถูกยืนยันตัวตนแล้ว** แต่ role ที่ได้
ไม่มีสิทธิ์ (ถ้าอ่าน key ไม่ได้เลย ระบบจะเงียบ ไม่มี error แบบนี้) เหลือสาเหตุสองอย่าง:

### สาเหตุที่ 1 — key ไม่ใช่ของ service_role

key ของ `anon` กับ `service_role` **หน้าตาเหมือนกันทุกประการ** — เป็น JWT ยาว
ประมาณ 200 ตัวอักษรทั้งคู่ ต่างกันแค่ claim `role` ข้างใน วางสลับช่องแล้วความยาว
กับ checksum ยัง "ตรง" ทุกอย่าง

**ตรวจได้สองทาง:**

```bash
npm run check-env        # แสดง role=service_role ✓ หรือ role=anon ⚠️
pm2 logs | grep '\[supabase\]'   # บรรทัดตอนเริ่มระบบ
```

ตอนเริ่มระบบจะขึ้นบรรทัดใดบรรทัดหนึ่ง:

| log | แปลว่า |
| --- | --- |
| `service client พร้อมใช้งาน role=service_role` | ใช้ได้ |
| `... มีค่าเป็น key ของ role "anon" ...` | วางสลับช่อง — ระบบปฏิเสธไม่สร้าง client แล้วใช้ cache ใน memory แทน |
| `... อ่าน role ข้างในไม่ออก ...` | ไม่ใช่ JWT (อาจเป็น key รูปแบบใหม่) — ใช้งานต่อตามปกติ |

### สาเหตุที่ 2 — ยังไม่ได้ให้สิทธิ์ service_role ใน DB

`0003`/`0004` ไม่เคย `grant` ให้ `service_role` เลย — อาศัยว่า Supabase ตั้ง
`ALTER DEFAULT PRIVILEGES` ไว้ให้อัตโนมัติ ซึ่ง**ไม่จริงเสมอไป** โปรเจกต์ที่ปิด
auto-expose ของ PostgREST มักถอด default privileges ออกด้วย

ฟังก์ชันมีปัญหาชัดกว่านั้น: PostgreSQL ให้ `EXECUTE` กับ `PUBLIC` เป็นค่าเริ่มต้น
ซึ่ง `service_role` ได้มาทางอ้อม พอ `0004` สั่ง `revoke all on function ... from public`
สิทธิ์นั้นก็หายไปด้วยถ้าไม่มี grant ตรงๆ มารองรับ

**แก้: รัน `supabase/migrations/0005_service_role_grants.sql`** ซึ่งเขียน grant ให้
`service_role` ตรงๆ ทั้งสี่ตารางและฟังก์ชัน (ไม่ผ่อนเกราะของ `anon`/`authenticated`
เลยแม้แต่น้อย และรันซ้ำได้ปลอดภัย)

ตรวจผลด้วย query ที่อยู่ท้ายไฟล์ migration นั้น

### กันไม่ให้เกิดซ้ำ

`lib/supabase/service.test.ts` ตรวจสามชั้นที่เทสต์ตรรกะจับไม่ได้:

1. **runtime** — สร้าง client แบบเดียวกับของจริงแล้วดัก header ที่ออกไป ยืนยันว่า
   `Authorization: Bearer <service key>` และไม่มี session ของผู้ใช้มาแทนที่
2. **โครงสร้าง** — ไม่มีไฟล์ไหนนอกทางเข้าแตะตารางของกลาง และทางเข้าต้องไม่ใช้
   client ที่ถือ anon key หรือ session ผู้ใช้
3. **migration** — ทุกตารางและฟังก์ชันมี grant ให้ `service_role` เขียนไว้ชัดๆ

## Deploy หลัง Nginx

session ของ Supabase ถูกเก็บใน cookie ที่ใหญ่กว่าปกติมาก (JWT + ข้อมูลผู้ใช้จาก Google
รวมแล้วประมาณ 4–6 KB ถูกหั่นเป็นหลายก้อน ก้อนละไม่เกิน 3180 bytes) ตอนเข้าสู่ระบบสำเร็จ
`/auth/callback` จะตอบกลับมาพร้อม `Set-Cookie` หลายอันรวมกันเกิน 4 KB

ค่าเริ่มต้นของ Nginx (`proxy_buffer_size` 4k) เล็กเกินกว่าจะรับ response header ขนาดนั้น
ผลคือ Nginx ตอบ **502 Bad Gateway ทันที** และ log ของแอพจะไม่มี error อะไรเลย เพราะฝั่งแอพ
ตอบถูกต้อง แต่ Nginx เป็นฝ่ายปฏิเสธเอง (ใน `/var/log/nginx/error.log` จะเห็นข้อความ
`upstream sent too big header`)

ต้องขยาย buffer ใน server block:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;

    proxy_set_header Host              $host;
    proxy_set_header X-Forwarded-Host  $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP         $remote_addr;

    # จำเป็นสำหรับ cookie ของ Supabase ค่าเริ่มต้น 4k เล็กเกินไปทำให้เกิด 502
    proxy_buffer_size       16k;
    proxy_buffers        8  16k;
    proxy_busy_buffers_size 32k;
}
```

`X-Forwarded-Host` กับ `X-Forwarded-Proto` จำเป็นด้วย ไม่งั้น `/auth/callback` จะ redirect
ผู้ใช้กลับไปที่อยู่ภายในของเครื่องแทนที่จะเป็นโดเมนจริง

ทุกการเรียก Supabase ตั้งเพดานเวลาไว้ที่ 8 วินาที (`lib/supabase/fetch.ts`) เพื่อไม่ให้
request ค้างรอจนโดน reverse proxy ตัดแล้วกลายเป็น 502/504 โดยไม่มีร่องรอยใน log
